## PIX 변경이 아닌 것 (범위 밖)

**다유형 OCPN 공동 정렬**은 PIX 미구현 요구가 아니다. 기준 SHA에서 `align_object_log`(`src/pix/compute/object_conformance.py`)가 명시 범위 이벤트에 대한 제한된 joint alignment를 제공한다. WMC 분석 파이프라인에 해당 연산을 연결·보고하는 것은 **소비자(파이프라인) 배선 과제**로 둔다. 본 문서에서 실행 검증은 하지 않았다.

## 채택 요구사항 (우선순위순)

### 1. `tie_policy="concurrent"` 트레이스를 재생·정밀도·발견·정렬 연산이 수용

| | |
| --- | --- |
| **우선순위** | 최상 (높음) |
| **변경 요지** | `reconstruct_traces`·`measure_temporal`·`evaluate_constraints`와 같이 concurrent 트레이스를 받는 경로와, `replay_traces`·`measure_prefix_precision`·`discover_process_tree`·`align_traces`·`discover_dfg` 등 **순서 전제 연산**의 거절 정책을 한 체계로 맞춘다. 즉시 전 구간 partial-order 시맨틱을 내기 어렵다면, 연산별로 거절·부분 결과·대체 정책의 의미를 공식 문서와 API 진단에 고정한다. |
| **배경** | WMC 원천 로그는 분 단위 관측이 많아 동률이 흔하다. 시간 측정만 concurrent로 두고 적합성·재생·발견에서는 `event_id` 사전순 우회를 쓰면 **같은 로그에서 전제가 갈라진다**. 통합 검토에서 지표·적합성 파이프라인이 이 불일치로 막히거나 우회한 사례가 반복 보고되었다. |

**현재 동작 (기준 SHA `6e9af5ee`, 소스 확인)**

- `reconstruct_traces`는 `TraceSpec.tie_policy=="concurrent"`일 때 겹치는 관측 구간을 `order_group`으로 묶는다(`src/pix/compute/trace.py`, `TRACE_OPERATOR_ID = "pix.reconstruct_traces"`).
- `measure_temporal`은 concurrent 트레이스를 처리한다(`src/pix/compute/temporal.py`).
- `evaluate_constraints`는 concurrent 그룹을 전제로 한다(`src/pix/compute/constraints.py`).
- 아래 연산은 부모 `TraceSet`의 `tie_policy=="concurrent"`이면 `INVALID_INPUT`으로 거절하며, 공통 진단 코드 **`concurrent_traces_unsupported`**를 쓴다.
  - `replay_traces` — `src/pix/compute/replay.py` (약 337–348행)
  - `measure_prefix_precision` — `src/pix/compute/precision.py` (약 279–288행)
  - `discover_process_tree` — `src/pix/compute/discovery.py` (약 506–511행)
  - `align_traces` — `src/pix/compute/conformance.py` (약 182–192행, `ALIGNMENT_OPERATOR_ID = "pix.align_traces"`)
- `discover_dfg`는 동일 정책이나 진단 코드가 **`concurrent_dfg_unsupported`**이다(`src/pix/compute/dfg.py`, 약 89–101행).
- 사용자 가이드는 DFG·발견·정렬·재생·prefix precision이 concurrent를 **명시적 부분순서 정의 전까지 거절**한다고 서술한다([`CHAT_HANDOVER_AND_TIME_PRECISION.md`](../user-guide/CHAT_HANDOVER_AND_TIME_PRECISION.md) 72–74행).

**수락 기준**

- 동일 `TraceSet`(concurrent 정책·동일 `TimePrecision`)으로 위 연산군을 호출했을 때, **거절·부분·정상** 상태와 진단이 문서·API 계약과 일치한다.
- 연산별로 “왜 순서가 필요한지”와 concurrent 입력 시 **허용되는 대체**(예: 명시 `event_id` 정책 재구성, partial envelope)가 소비자 가이드에 적혀 있다.
- 회귀: 기존 `tie_policy="event_id"`·`reject` 경로의 결정론적 동작이 깨지지 않는다.

### 2. 속성 값 조건이 들어간 적합성 (data-aware, 범위 축소)

| | |
| --- | --- |
| **우선순위** | 높음 (2순위) |
| **변경 요지** | (a) 규칙 **활성화**를 이벤트·객체 **속성 값 술어**로 거는 것. (b) `Response`·`Precedence` 등 이진 규칙에서 짝을 **동일 속성 값**(예: 동일 실패 서명)을 가진 발생끼리만 맺는 것. |
| **배경** | 임무 감사·에이전트 실행 렌즈 적합성에서 “같은 실패인지”“`external_write=true`인지” 같은 판정이 필요하다. 현재는 어댑터가 activity 라벨에 판정을 붙이는 우회만 있어 **판정 근거가 PIX 결과 밖**에 남는다. |

**현재 동작 (기준 SHA)**

- 선언 규칙 형식(`src/pix/contracts/constraint.py`)의 `ResponseRule`·`PrecedenceRule`·`TimedResponseRule` 등은 **activity 이름 쌍**만 갖고 속성 조건 필드가 없다.
- `evaluate_constraints`(`src/pix/compute/constraints.py`, `pix.evaluate_constraints`)는 위 규칙과 트레이스 순서·시간 정밀도를 평가한다.
- `evaluate_filter_predicates`(`src/pix/object_centric/filter_predicates.py`)는 속성 같음·범위·존재 등으로 **부분 로그 선택** 증거를 낸다. 이는 적합성 규칙이 아니라 필터 술어이다.
- (a)에 대해 “필터로 부분 로그를 만든 뒤 `evaluate_constraints`” 조합이 공식적으로 허용·문서화되는지는 **확인 필요** — 저장소에 소비자 조합 가이드는 본 문서 작성 시 찾지 못했다.

**수락 기준**

- (b)에 대해: 동일 속성 값 짝짓기가 `RuleEvaluation`·witness에 **재현 가능한 근거**로 남는다.
- (a)에 대해: 규칙 활성화 술어가 없으면, (a)를 필터+적합성 조합으로 대체할 수 있다는 것이 **명시적 계약**(허용/금지·한계)으로 적혀 있거나, 규칙 타입에 활성화 조건이 추가된다.
- 기존 activity-only 규칙의 출력 계약은 하위 호환을 유지한다.

### 3. 벽시계 없이 순서만 있는 이벤트 입력 계약

| | |
| --- | --- |
| **우선순위** | 중간 (3순위) |
| **변경 요지** | `Event.time`에 timezone-aware `datetime`을 강제하는 현 모델과 별도로, **순서 전용 로그**를 공식 입력으로 받는 계약을 제공한다. `null` 타임스탬프 허용 여부는 PIX 설계 결정으로 두되, WMC 쪽 요구는 “합성 절대시각 없이 순서만으로 분석 가능”이다. |
| **배경** | 에이전트 렌즈 등 원천은 상대 경과 시간만 있고, Process Excellence 허브 봉투 대량 중 관측 시각이 비어 있는 비율이 컸다(통합 보고: 2,747개 중 1,974개 null — **허브 봉투 기준 수치**). 현재는 절대시각을 합성해 넣거나 해당 이벤트를 OCEL에 넣지 않는다. |

**현재 동작 (기준 SHA)**

- `Event.time`은 `__post_init__`에서 `_require_aware_time`으로 검증된다(`src/pix/ocel/model.py`, 약 193–205행). `null`·naive datetime은 받지 않는다.
- `reconstruct_traces`는 이벤트 시간 간격·`TimePrecision`에 의존한다(`src/pix/compute/trace.py`).

**수락 기준**

- 순서 전용 입력(별도 필드·별도 로그 프로파일·기타 PIX가 선택한 형태)이 **import/검증 경로**에 문서화된다.
- 해당 입력으로 최소한 트레이스 재구성 또는 순서 기반 연산 중 **하나의 공식 연산**이 end-to-end로 동작한다.
- 합성 절대시각을 강제하지 않는 소비자 시나리오가 사용자 가이드에 예시로 있다.

### 4. DFG용 `build_visualization` 네이티브 어댑터

| | |
| --- | --- |
| **우선순위** | 중간 (4순위) |
| **변경 요지** | `discover_dfg` 결과(`DirectlyFollowsGraph` 또는 해당 `ComputationResult`)를 `build_visualization`이 OCDFG와 같이 `VisualizationDocument`로 어댑트한다. |
| **배경** | WMC 대시보드 파이프라인은 초기부터 `build_visualization` 경로를 쓰다 DFG에서 실패하여, `build_graph`·`export_html` 우회를 썼다. 통합 시험에서 직접 DFG 시각화 호출 실패가 반복 기록되었다. |

**현재 동작 (기준 SHA)**

- `build_graph`는 `ComputationResult` 값이 `DirectlyFollowsGraph`이면 `GraphDocument`를 만든다(`src/pix/viewer/adapter.py`, 약 40–47행).
- `build_visualization`(`src/pix/viewer/visualization.py`)은 입력 타입별로 `case_panels` / `object_panels` / `model_panels` 등을 시도하고, 어댑터가 없으면 `UnsupportedVisualizationError`를 낸다(약 391–395행).
- `visual_object_adapters.py`에 `ObjectCentricDFG`용 `_ocdfg`는 있으나, **`DirectlyFollowsGraph`용 `build_visualization` 어댑터는 확인되지 않았다**.

**수락 기준**

- `build_visualization(dfg_result)`(또는 문서화된 동등 호출)이 `UnsupportedVisualizationError` 없이 `VisualizationDocument`를 반환한다.
- 패널·provenance에 source digest·computation id가 OCDFG 어댑터와 동급으로 남는다.
- 기존 `build_graph` 경로는 회귀 없이 유지된다.

- CI 또는 문서의 최소 스모크가 추가된다(구현 방식은 PIX가 선택).

### 6. 이종 활동을 상위 활동으로 접는 변환

| | |
| --- | --- |
| **우선순위** | 낮음 (6순위) |
| **변경 요지** | 서로 다른 activity(또는 kind) 여러 개를 **하나의 상위 activity**로 묶고, 접기 규칙·출처를 PIX 연산 결과로 남기는 공식 변환. |
| **배경** | 에이전트 렌즈 등에서 도구 호출·추론·검사 단계를 상위 단계로 묶어 적합성을 보려면, 현재는 외부 변환기가 activity를 합치고 규칙표만 증거로 남기는 수준이다. |

**현재 동작 (기준 SHA)**

- `merge_ocel_events`(`src/pix/object_centric/transformations.py`, 약 753–761행)는 **동일 activity·동일 시각** 이벤트 병합과 공유 객체 컴포넌트 병합만 다룬다.
- `fold` / `roll_up` / `unfold` / `drill_down`(`src/pix/object_centric/cube.py`)은 **이벤트 타입·객체 참여 기준 큐브 연산**(정확 역연산 계획)이며, 임의 이종 activity를 시간 구간 없이 상위 단계로 접는 연산은 아니다.

**수락 기준**

- 접기 규칙(매핑 표 또는 선언 스펙)과 변환된 OCEL/트레이스가 `ComputationResult`로 반환된다.
- 적용된 접기가 evidence·digest에 남아 소비자가 “어떤 규칙으로 접혔는지” PIX 결과만으로 재현할 수 있다.
- 기존 `merge_ocel_events`·큐브 연산의 의미는 변경되지 않는다.

### 7. `tie_policy="event_id"` 순서 규칙 명시 (1번과 동일 이슈 묶음)

| | |
| --- | --- |
| **우선순위** | 낮음 (7순위, **1번과 한 이슈로 추적**) |
| **변경 요지** | concurrent를 쓸 수 없는 연산에서 `event_id` 정책으로 우회할 때, **문자열 사전순**이 순서 규칙임을 API·가이드에 명시한다. 패딩하지 않은 id에서 `evt_9`가 `evt_10`보다 뒤로 가는 함정을 문서화하고, 필요 시 숫자·삽입 순 옵션을 검토한다. |
| **배경** | 1번 미해결 시 소비자가 사실상 유일한 우회인데, 사전순이 비직관적이면 조용히 잘못된 순서 전제가 생긴다. |

**현재 동작 (기준 SHA)**

- 트레이스 내 이벤트 정렬 키는 `(event.time, event.id)`이다(`src/pix/compute/trace.py`, 약 46–48행).
- `tie_policy="event_id"`일 때 동일 시간대는 id 사전순으로 순서를 깨며, `timestamp_tie_broken` 진단을 남긴다(약 93–100행).
- 사용자 가이드는 equal timestamps를 event id로 정렬할 때 **인과 증거가 아님**을 명시한다([`CHAT_HANDOVER_AND_TIME_PRECISION.md`](../user-guide/CHAT_HANDOVER_AND_TIME_PRECISION.md)).

**수락 기준**

- `TraceSpec.tie_policy` 설명과 1번 연산군 거절 문서에 **사전순 규칙·패딩 함정**이 포함된다.
- 1번이 해결되어 concurrent가 연산별로 수용되면, 7번은 문서 유지 수준으로 축소해도 된다(Traccia 메모).
